# Engine analyzers

This page is the reference for the diagnostics of the engine analyzers: the
rule behind each one, an example that breaks it, and a correction. The
analyzers are in [`tools/Nobara.Analyzers`](../../tools/Nobara.Analyzers/README.md).

## Where they apply

[`Nobara.Sdk`](../../tools/Nobara.Sdk/README.md) attaches the analyzers to
every module, extensions included, and to script facades (`.Scripting`). A
project declares nothing to receive them. Tests, benchmarks, and build-time
tools (`.Build`, `.Generators`, `.Analyzers`, `.TypeGen`) are not checked.

Every diagnostic is an error. Generated code is not checked: for example a
file that starts with an `<auto-generated>` comment, or whose name ends with
`.g.cs`.

## Recognized attributes

The analyzers recognize three attributes by their full name. They do not
reference the assembly that defines them.

| Attribute | Targets | Meaning |
| --- | --- | --- |
| `Nobara.Core.HotPathAttribute` | class, struct, interface, method, constructor, property | The code is a hot path. |
| `Nobara.Core.LoopCallbackAttribute` | class, struct, interface, method | A loop phase runs the code. |
| `Nobara.Core.UsesOptionalDependencyAttribute(string moduleId)` | class, several times | The class is an isolation class for the optional dependency `moduleId`. |

A method is marked `[HotPath]` or `[LoopCallback]` when one of these carries
the attribute:

- the method itself;
- the property it is an accessor of;
- its containing type, unless the method is a static constructor;
- a method it overrides, or an interface method it implements.

A nested type is not covered by the mark of the type that contains it. A mark
on an interface method covers every implementation, so a contract marks its
implementations once:

```csharp
public interface ICropGrowth
{
    [HotPath]
    void Grow(Span<CropCell> cells);
}

public sealed class WheatGrowth : ICropGrowth
{
    // Checked as hot path code: it implements a marked method.
    public void Grow(Span<CropCell> cells) { /* ... */ }
}
```

## Hot path rules

The rules `NOB101` to `NOB105` apply to the bodies of methods,
constructors, accessors, and operators marked `[HotPath]`, including the
lambdas and local functions they contain, and to the instance field and
property initializers of a type marked `[HotPath]`.

Two kinds of code are exempt, because they do not run on the hot path:

- code inside a `throw` statement or expression, such as the message of an
  exception;
- the operand of `nameof`.

### NOB101

**Rule.** Hot path code does not allocate managed memory. The diagnostic
names the construct:

| Construct | Allocates |
| --- | --- |
| `new` of a class, a record class, or a delegate | always |
| `new T()` | when `T` is not constrained to `struct` |
| array creation, including `params` arrays with at least one element | always |
| collection expression | unless its type is `Span<T>` or `ReadOnlySpan<T>`, or it is an empty array |
| anonymous type, `with` on a record class | always |
| string concatenation with `+` or `+=` | unless the result is a constant |
| interpolated string | unless the callee takes it through an interpolated string handler of its own |
| delegate created from a method group | unless the method is static (cached since C# 11) |
| `foreach` whose enumerator is a reference type | for example over an `IEnumerable<T>` |
| iterator method (`yield`) | always |

A lambda or anonymous method that captures nothing is cached by the
compiler and is allowed; one that captures is reported by `NOB103`.

**Example.**

```csharp
[HotPath]
public int CountRipe(IEnumerable<CropCell> cells)
{
    var ripe = new List<CropCell>();      // NOB101: new 'List<CropCell>'
    foreach (CropCell cell in cells)      // NOB101: foreach enumerator of type 'IEnumerator<CropCell>'
    {
        if (cell.IsRipe) ripe.Add(cell);
    }

    return ripe.Count;
}
```

**Correction.** Take a span, and count without a collection.

```csharp
[HotPath]
public int CountRipe(ReadOnlySpan<CropCell> cells)
{
    int ripe = 0;
    foreach (CropCell cell in cells)
    {
        if (cell.IsRipe) ripe++;
    }

    return ripe;
}
```

### NOB102

**Rule.** Hot path code does not use LINQ: no call to a method of
`System.Linq.Enumerable`, `Queryable`, `ParallelEnumerable`, or
`AsyncEnumerable`, and no query expression.

**Example.**

```csharp
[HotPath]
public int TallestStalk(int[] heights) => heights.Max(); // NOB102: 'Enumerable.Max'
```

**Correction.** Write the loop.

```csharp
[HotPath]
public int TallestStalk(ReadOnlySpan<int> heights)
{
    int tallest = 0;
    foreach (int height in heights) tallest = Math.Max(tallest, height);
    return tallest;
}
```

### NOB103

**Rule.** Hot path code does not create closures: no lambda, anonymous
method, or local function that captures a local variable, a parameter, or
`this`. The diagnostic names the first captured variable.

**Example.**

```csharp
[HotPath]
public void Water(Span<CropCell> cells, int amount)
{
    ForEach(cells, cell => cell.Water += amount); // NOB103: lambda captures 'amount'
}
```

**Correction.** Write the loop, or make the function `static` and pass the
state as an argument.

```csharp
[HotPath]
public void Water(Span<CropCell> cells, int amount)
{
    foreach (ref CropCell cell in cells) cell.Water += amount;
}
```

### NOB104

**Rule.** Hot path code does not box value types:

- no conversion of a value type to `object`, `ValueType`, `Enum`, or an
  interface, including `params object[]` arguments;
- no call to a method of `object`, `ValueType`, or `Enum` that the struct
  does not override, such as `GetHashCode`, `ToString`, or `GetType`. Calls
  on enum values box.

**Example.**

```csharp
[HotPath]
public int Hash(CropCell cell) => cell.GetHashCode(); // NOB104: call to 'ValueType.GetHashCode()', inherited by 'CropCell'
```

**Correction.** Override the method in the struct, and mark it.

```csharp
public struct CropCell
{
    public int Kind;
    public int Growth;

    [HotPath]
    public override int GetHashCode() => HashCode.Combine(Kind, Growth);
}
```

### NOB105

**Rule.** Hot path code calls only marked code of its own project. A method,
constructor, property or indexer accessor, or user-defined operator or
conversion that is declared in the same project and called from hot path
code is marked `[HotPath]`, directly or by one of the ways listed in
[Recognized attributes](#recognized-attributes). The analyzer then checks it
as well, so the rules hold along every call chain inside the project.

These calls need no mark:

- calls into another assembly, the .NET libraries and other modules included;
- auto-implemented property accessors, and members the compiler generates;
- local functions and lambdas, which are part of the calling code;
- `extern` methods and partial methods without an implementation.

A call to an abstract or interface method of the project needs a mark on that
method or its type, which then covers every implementation.

**Example.**

```csharp
public static class Soil
{
    public static int Fertility(int moisture) => moisture * 2;
}

[HotPath]
public int Yield(int moisture) => Soil.Fertility(moisture); // NOB105: calls 'Soil.Fertility(int)'
```

**Correction.** Mark the callee, or its type.

```csharp
[HotPath]
public static class Soil
{
    public static int Fertility(int moisture) => moisture * 2;
}
```

## Static state rules

The rules `NOB201` to `NOB203` apply to all checked code. The contexts of a
process, such as a client and its integrated server, share every static
member, so the code of a module keeps its state in instances.

These static members are allowed:

- constants;
- `static readonly` fields of a type that is not listed below, such as a
  string, a primitive, an enum, a struct, `ImmutableArray<T>`, a frozen
  collection, or `IReadOnlyList<T>`;
- properties without a setter that compute their value, and get-only
  auto-properties of such a type;
- events with explicit `add` and `remove` accessors.

### NOB201

**Rule.** No static field that is not `readonly`, and no `[ThreadStatic]`
field, even `readonly`.

**Example.**

```csharp
public static class Harvest
{
    private static int s_total; // NOB201
}
```

**Correction.** Keep the value in an instance that the module owns.

```csharp
public sealed class HarvestTally
{
    private int _total;
}
```

### NOB202

**Rule.** No static property with a setter, and no static field-like event.

**Example.**

```csharp
public static class Season
{
    public static int Day { get; set; }     // NOB202: static property
    public static event Action? DayChanged; // NOB202: static event
}
```

**Correction.** Move the property and the event to an instance, such as a
service of the module.

### NOB203

**Rule.** No `static readonly` field and no static get-only auto-property of
a mutable type: an array, or a type below, a class derived from a class
below, or an interface below.

| Namespace | Types |
| --- | --- |
| `System.Collections.Generic` | `List<T>`, `Dictionary<TKey, TValue>`, `HashSet<T>`, `Queue<T>`, `Stack<T>`, `LinkedList<T>`, `SortedDictionary<TKey, TValue>`, `SortedList<TKey, TValue>`, `SortedSet<T>`, `PriorityQueue<TElement, TPriority>`, `ICollection<T>`, `IList<T>`, `IDictionary<TKey, TValue>`, `ISet<T>` |
| `System.Collections` | `ArrayList`, `BitArray`, `Hashtable`, `Queue`, `SortedList`, `Stack`, `IList`, `IDictionary` |
| `System.Collections.Concurrent` | `BlockingCollection<T>`, `ConcurrentBag<T>`, `ConcurrentDictionary<TKey, TValue>`, `ConcurrentQueue<T>`, `ConcurrentStack<T>` |
| `System.Collections.ObjectModel` | `Collection<T>`, `KeyedCollection<TKey, TItem>`, `ObservableCollection<T>` |
| `System`, `System.IO`, `System.Text`, `System.Threading` | `Random`, `Stream`, `StringBuilder`, `AsyncLocal<T>`, `ThreadLocal<T>` |

**Example.**

```csharp
public static class Crops
{
    public static readonly string[] Names = { "wheat", "barley" }; // NOB203: holds a mutable 'string[]'
}
```

**Correction.** Use an immutable collection.

```csharp
public static class Crops
{
    public static readonly ImmutableArray<string> Names = ["wheat", "barley"];
}
```

## Asynchronous code rule

### NOB301

**Rule.** Code marked `[HotPath]` or `[LoopCallback]` is not `async`: no
`async` method, and no `async` lambda or local function inside such code.
Asynchronous code allocates and resumes on threads that the loop does not
control. Computations run as jobs, and asynchronous I/O starts outside the
loop and posts its result to the synchronization point of the context.

**Example.**

```csharp
public interface IFarmStep
{
    [LoopCallback]
    void Update();
}

public sealed class Irrigation : IFarmStep
{
    public async void Update() => await LoadForecastAsync(); // NOB301: method 'Update' is async
}
```

**Correction.** Keep `Update` synchronous, and apply the result of the
asynchronous operation when it reaches the loop thread.

## Optional dependency rules

A module references an optional dependency like any other, but its code must
load when the assembly of that dependency is absent. The .NET runtime fails
as soon as it compiles a method or loads a type that mentions a type of a
missing assembly. Code that uses an optional dependency therefore lives in
*isolation classes*, which the module calls only once it has checked that the
dependency is present.

The identifiers of the optional dependencies come from `module.nobara`,
through the `NobaraOptionalModules` build property (see
[the `module.nobara` reference](formats/module-nobara.md#dependencies)). The
assembly of a dependency is the referenced assembly whose name equals the
identifier, compared without case.

### NOB401

**Rule.** A type of an optional dependency, or a member of such a type, is
used only inside a class marked
`[UsesOptionalDependency("<identifier>")]` for that dependency, or inside a
type nested in it. The diagnostic is reported once per statement or
declaration. `using` directives, `nameof`, and documentation comments are
not uses.

**Example.**

```csharp
public sealed class FieldRenderer
{
    private Weather.RainService? _rain; // NOB401: 'RainService' belongs to the optional dependency 'farm.weather'
}
```

**Correction.** Move the code into an isolation class, and call it only when
the dependency is present.

```csharp
[UsesOptionalDependency("farm.weather")]
internal sealed class RainBridge
{
    private readonly Weather.RainService _rain;

    public RainBridge(object rainService) => _rain = (Weather.RainService)rainService;

    public float Wetness(int x, int z) => _rain.WetnessAt(x, z);
}
```

### NOB402

**Rule.** An isolation class does not expose the types of an optional
dependency: its base class, its interfaces, and the signatures of its members
that are not private (field and property types, return and parameter types)
do not mention them. The same applies to the types nested in it that are not
private. Code outside the class would otherwise load those types when it
calls the class.

**Example.**

```csharp
[UsesOptionalDependency("farm.weather")]
internal sealed class RainBridge
{
    public Weather.RainService Service { get; } // NOB402
}
```

**Correction.** Expose only types of the module or of required dependencies,
as `Wetness` does in the example of `NOB401`.

### NOB403

**Rule.** The identifier given to `[UsesOptionalDependency]` is declared as an
optional dependency in `module.nobara`.

**Example.**

```csharp
[UsesOptionalDependency("farm.wether")] // NOB403: 'farm.wether' is not an optional dependency of this module
internal sealed class RainBridge { }
```

**Correction.** Fix the identifier, or declare the dependency with
`optional="true"`.

## Known limitations

- No assembly of the engine defines the recognized attributes yet; a module
  that uses them declares them itself, in the `Nobara.Core` namespace.
- `NOB105` does not follow calls through delegates, nor implicit calls such
  as `GetEnumerator` in `foreach`, `Dispose` in `using`, or `Deconstruct`.
- `NOB105` reports a call to a throw helper of the project, such as
  `ThrowHelper.OutOfRange()`, unless the helper is marked: only `throw`
  itself is exempt.
- Strings built by calls into the .NET libraries, such as `int.ToString()`
  or `string.Format`, are not reported, because calls into other assemblies
  are not followed. Their boxed arguments are reported by `NOB104`.
- `[HotPath]` on a lambda or a local function has no effect; the mark of the
  enclosing member covers it.
- `NOB203` recognizes mutable types from the list above only. A
  `static readonly` field of a mutable class of the module is not reported.
- The analyzers do not check that an isolation class is called only when its
  dependency is present.
- The analyzers provide no code fixes.
